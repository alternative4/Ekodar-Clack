# Расчёт расхода соли для клапана Clack EM.S (Ekodar MQTT)

Документ — спецификация для задач t_6718b8d8 (учёт уровня соли) и t_3dc7971b
(предупреждение «досыпать соль»). Источник данных: ночная запись телеметрии
`/home/dankaz/clack/cap/clack_mqtt.jsonl` (регенерация 2026-09-17 01:11:56–04:50:26 МСК)
и секции настроек клапана (cmd 201/202/203/206/208).

## 1. Что клапан знает, а что — нет

Клапан **не измеряет массу соли**. В MQTT-телеметрии нет поля расхода соли:

- `cmd=100` (standby): `current-flow, cap-max, cap-remain, rssi, day-remain` — только объём/ёмкость;
- `cmd=110` (regeneration): `cycles, total-time, total-remain, current-cycle, cycle-time, repeat-num, dissolve` — только фазы и время;
- `section 206` (Regen-Settings): длительности фаз (на этом клапане: Fill 5.25,
  Softening 120, Backwash 10, Regenerant Draw Up 60, Backwash 10, Rinse 10) —
  время просола, а не кг соли.

Следовательно **kg на регенерацию — вход от человека** (мешок и наблюдение
«на сколько регенераций хватает мешок»), а **число регенераций даёт клапан**
(детект по телеметрии). Клапан нужен как счётчик знаменателя.

## 2. Формула и единицы (зафиксированы)

```
kg_per_regeneration = bag_mass_kg / regenerations_per_bag        [кг/рег.]
salt_remaining_kg   = salt_remaining_kg_before − kg_per_regeneration   [кг]
regen_remaining     = floor(salt_remaining_kg / kg_per_regeneration)    [рег.]
warn_threshold_kg   = salt_warn_remaining_regens * kg_per_regeneration  [кг]
```

Единицы: всё в килограммах (кг) и регенерациях (шт). Время регенерации и
flow в расчёт соли не входят. Обратная форма (если человек знает расход
регенерации из инструкции по настройке, а не число регенераций на мешок):

```
regenerations_per_bag = bag_mass_kg / kg_per_regeneration
```

Запрещено хранить промежуточные значения в тоннах/фунтах/литрах.

## 3. Детект регенерации из данных клапана (знаменатель)

Подтверждено записью 2026-09-17:

- переход `command: 100 → 110` = старт регенерации (первый cmd=110 в 01:11:56);
- возврат `110 → 100` = конец (04:50:55); во время регенерации клапан
  параллельно шлёт 100 и 110 (~1 с apart) — дедупликация обязательна;
- **надёжный сигнал «рег. состоялась»**: ап-джамп `cap-remain` ≥ 0.5·`cap-max`
  (наблюдено 1581 → 6556 при cap-max 6557 между 01:20:55 и 01:21:25).

Дедуп-окно: **6 ч** (регенерация шла 3 ч 38.5 мин = total-time 13066 с; окно
должно покрывать полную длительность с запасом ×1.6). Событие = один инкремент
счётчика регенераций и одно списание `kg_per_regeneration`.

Калибровка `regenerations_per_bag` человеком: пользователь отмечает дату
замены мешка; число регенераций между отметками, посчитанное интеграцией по
событиям выше, и есть знаменатель. Либо человек вводит число вручную («мешок
на ~10 регенераций»).

## 4. Пример расчёта (принятые эталонные числа)

Дано: мешок 25 кг; пользователь наблюдает, что мешка хватает на 10 регенераций;
порог предупреждения N = 2 регенерации.

```
kg_per_regeneration = 25 / 10 = 2.5 кг/рег.
warn_threshold_kg   = 2 × 2.5 = 5.0 кг
```

Насыпали мешок: `salt_remaining_kg = 25.0`. После 8 регенераций:
`25.0 − 8×2.5 = 5.0 кг` → `regen_remaining = 2` → предупреждение ещё не
активно (строго: активно при `regen_remaining < N`, т.е. после 9-й регенерации
останется 2.5 кг → `regen_remaining = 1 < 2` → предупреждение). К 10-й регенерации
остаток упирается в 0 → активен алерт «мешок кончился».

Сверка с этим клапаном: график регенераций — среда+суббота (section 201),
≈ 8–9 рег./мес ⇒ мешок 25 кг ≈ на 5–6 недель; предупреждение при пороге
N=2 приходит за ~7–8 дней до конца мешка.

## 5. Поля конфигурации (для config/options flow интеграции clack_ekodar)

| Ключ | Тип | Дефолт | Описание / валидация |
|---|---|---|---|
| `salt_bag_mass_kg` | float | 25.0 | Масса одного мешка, кг. `> 0` (vol.Range(min=0.1, max=500)). |
| `salt_regen_per_bag` | float \| None | None | Регенераций на мешок, шт. `> 0`. Может быть None, если задан `salt_kg_per_regen`. |
| `salt_kg_per_regen` | float \| None | None | Прямойoverride среднего расхода, кг/рег. Имеет приоритет над `salt_regen_per_bag`. |
| `salt_tank_max_kg` | float | 75.0 | Физический потолок солерастворителя (clamp после «добавить мешок»), кг. |
| `salt_warn_remaining_regens` | int | 2 | Предупреждать, когда `regen_remaining < N`. |
| `salt_warn_floor_kg` | float \| None | None | Аварийный запасной порог в кг, используется только если производная в кг/рег недоступна (см. п.6, строка «нет данных»). |

Производные, вычисляемые при запуске и при изменении options:
`kg_per_regen = salt_kg_per_regen if salt_kg_per_regen else bag_mass/regen_per_bag`.

Сущности для downstream-задач: `sensor.clack_salt_remaining_kg`,
`sensor.clack_salt_regen_remaining`, `binary_sensor.clack_salt_low`,
`button.clack_salt_added`, event `clack_regen_detected`.

## 6. Обработка краевых случаев

| Ситуация | Поведение |
|---|---|
| **Деление на ноль**: `salt_regen_per_bag` = 0/None и `salt_kg_per_regen` = None | `kg_per_regen = None`. НЕ считать, НЕ падать. Состояние «расход неизвестен»: списание не производится, предупреждение — только по `salt_warn_floor_kg` (если задан), либо предупреждение `salt_data_incomplete` («укажите расход соли») вместо ложного low. |
| `bag_mass ≤ 0` | Отклонить на валидации options flow (ошибка формы), в рантайме считать как None. |
| **Смена мешка** (нажата кнопка «Добавлена соль») | `salt_remaining_kg = min(salt_remaining_kg + bag_mass_kg, salt_tank_max_kg)`; сброс предупреждения; в истории событий зафиксировать дату замены — она же начало окна калибровки `regenerations_per_bag`. |
| **Неполный мешок** | Кнопка добавляет целый мешок; для частично досыпанного — service `add_salt` с параметром `kg` (по умолчанию = bag_mass). Событие пишется с фактической массой. |
| Регенерация при `remaining < kg_per_regen` | Списать до 0 (clamp, минимум не уходит в отрицательное), `regen_remaining = 0`, алерт активен. |
| **Нет данных / offline** (нет сообщения > `ONLINE_TIMEOUT_S`=120 с) | Значения заморожены (last-known), атрибут `stale=true`; предупреждение НЕ сбрасывается и НЕ усиливается по протухшим данным. |
| **Пропущенные регенерации за простой/рестарт HA** | `salt_remaining_kg` сохраняется (EntityRestore/запись в restore-state при каждом изменении). При рестарте события детекта за время простоя не догоняются — это осознанное упрощение; расхождение корректируется человеком кнопкой «Добавлена соль». |
| Пропущенное сообщение детекта (обрыв JSONL — наблюдались 3 битых payload за ночь) | Срабатывает второй (резервный) сигнал — ап-джамп cap-remain; внутри дедуп-окна 6 ч события не удваиваются. |
| day-remain после регенерации обновился не в момент сброса cap (cap сбросился в 01:21, day-remain 21→28 только в 04:50:55 — по завершении регенерации) | Для детекта конца регенерации day-remain НЕ использовать — только переход 110→100 / ап-джамп cap-remain. |

## 8. Предупреждение «досыпать соль» (реализовано, t_3dc7971b)

Слой предупреждений построен поверх модели `salt.py` без дублирования сущностей:

- `SaltModel.status()` → `{kind, level_kg, percent, regen_remaining,
  kg_per_regen, bags_recommended}`, где `kind`:
  - `ok` — остаток выше обоих порогов (`warn_kg` и `warn_regens`);
  - `low` — сработал один из порогов (то же, что `binary_sensor.needs_salt`);
  - `no_data` — уровень неизвестен (мешок ещё не «добавляли») — учёт не начат,
    а не «мало»: ложного low нет;
  - `incomplete` — **отложенное предупреждение**: уровень известен, но
    `kg_per_regen` вычислить нельзя (не заданы «промывок на мешок» и
    «кг на промывку») — предупреждение по остатку откладывается до
    дозаполнения настроек, текст сообщает об этом прямо.
- `sensor.clack_<MAC>_salt_status` — человекочитаемый статус (enum с
  переводами ru/en) + attrs `message_ru`/`message_en` с текстом рекомендации
  («Мало соли: осталось 2.5 кг, хватит на 1 промывку. Досыпьте 1 мешок и
  нажмите «Добавлена соль».») и машинными полями (`level_kg`,
  `regen_remaining`, `bags_recommended`).
- Сброс: `low → ok` автоматически при нажатии кнопки «Добавлена соль»
  (уровень поднимается на мешок). Уведомление из п.8.1 снимается тем же
  состоянием `ok`.

### 8.1 Пример persistent_notification (YAML-автоматизация в HA)

Готовый файл: `docs/salt-alert-automation.yaml`. Логика: показывать
уведомление при входе в `low`/`incomplete`, обновлять текст при смене

## 9. Критерии приёмки предупреждения (t_3dc7971b)

- Появляется при низком уровне: `kind=low` при `level < warn_kg` либо
  `regen_remaining < warn_regens` (тесты `test_low_by_*`).
- Исчезает после добавления: `add_bags` → `status()`=`ok`, binary_sensor
  сбрасывается автоматически (`test_reset_after_add_bags`).
- Не ложит при нормальном уровне: строго `<`, ровно на пороге — `ok`
  (`test_not_low_exactly_at_threshold`); неизвестный уровень ≠ low.
- Отложенное предупреждение при неполных данных регенераций: `incomplete`
  вместо ложного low (`test_incomplete_defers_warning`).
